# Design Bakeoff — 여러 모델 시안을 한 화면에서 비교해 좁혀가기

디자인 감각이 없어도(또는 시간이 없어도) 여러 후보를 나란히 놓고 "이건 되고 이건 안 되고"만
판정하면, 그 판정이 쌓여 점점 더 좋은 시안이 나오게 만드는 절차. **비유:** 요리 대회의
"베이크오프"처럼, 같은 재료(요구사항)로 여러 셰프(모델)가 각자 만든 걸 한 테이블에 놓고
맛만 보고 고른다 — 직접 요리할 줄 몰라도 된다.

## 전제
- `kairos` 스킬로 이미지 생성 모델(`gemini-2.5-flash-image`, `gpt-image-2` 등) 호출 가능
- `Artifact` 도구로 HTML 게시 가능
- 비자명한 스코프(다룰 범위·색 고정 여부 등)가 아직 안 정해졌다면 `deep-interview`로 먼저 좁힌다

## 절차

### 0단계 — 취향 문서 확인 (있으면)
`~/.claude/design-system/preferences.md`(범용 취향)와 `~/.claude/design-system/projects/<slug>.md`
(이 프로젝트 전용 확정 토큰·탈락 로그)가 있으면 먼저 읽는다. 이미 탈락한 스타일은 이번 라운드
프롬프트에서 자동으로 뺀다 — 같은 걸 또 만들어 비교시키면 시간 낭비다.

### 0-b단계 — 원칙 자가진단 (비용 없음, 취향과 무관)
후보를 만들기 전에 객관적 원칙 위반부터 먼저 잡는다 — 그리드·터치 영역·대비처럼 정답이 있는
항목은 취향 판단(accept/reject)에 맡길 필요가 없고, 여기서 걸러지면 이후 베이크오프 라운드
수 자체가 줄어든다(가설, 데이터 쌓이면 검증). 대상 화면에 아래 8개를 대조한다(출처: NN/g
10대 사용성 휴리스틱, 게슈탈트 원리, Apple HIG/Material Design 터치 타겟 가이드 —
2026-09-11 디자인베이스 "상품 상세 UI 개선하기" 영상 검토 중 확정):

1. **그리드/여백** — 마진 16·20·24 중 하나로 통일, 정렬 어긋남 없는지
2. **그룹핑** — 의미상 관련된 정보(가격+할인, 이름+평점)가 붙어 있는지 (게슈탈트 근접성·유사성)
3. **위계** — 크기·굵기·색으로 중요도가 구분되는지, 중요 정보는 스크롤해도 계속 보이는지
   (Nielsen "인식 vs 회상")
4. **터치 타겟** — 클릭 가능 요소가 44×44pt(iOS)/48×48dp(Android) 이상인지
5. **아이콘 일관성** — 필/스트로크 등 한 스타일로 통일됐는지 (Nielsen "일관성과 표준")
6. **대비/접근성** — 텍스트 대비 충분한지, 최소 폰트 12px 이상인지
7. **전경-배경** — 배경 노이즈가 핵심 요소를 가리지 않는지 (게슈탈트 전경-배경)
8. **오류 방지/상태 표시** — 로딩·빈 상태·에러 상태가 있는지 (Nielsen "오류 방지"·"시스템 상태 가시성")

여기서 잡힌 문제는 후보를 여러 개 만들 필요 없이 바로 고친다 — 정답이 있는 항목이라 베이크오프
(1~7단계) 대상이 아니다. 남은 주관적 요소(색·모양·톤)만 1단계로 넘어간다. **객관적 문제만
있고 주관적 선택이 남지 않으면 1단계 이후를 진행하지 않고 여기서 종료한다** — 후보 비교가
필요 없는 요청에 굳이 베이크오프를 강제하지 않는다.

커머스성 설득 패턴(소셜 프루프·희소성)은 이 체크리스트에 넣지 않았다 — 사내 도구·방송 관련
UI엔 대개 안 맞고, 필요한 프로젝트가 생기면 그때 프로젝트별로 추가한다.

### 0-c단계 — 기성 자산 확인 (자산을 직접 그리기 전, 2026-09-13 신설)

**트리거(관찰 가능)** — 아이콘·버튼 등 UI 자산을 직접 그리려는 순간(SVG `path`를 쓰기
시작하기 전, 또는 유니코드 글자로 아이콘을 대신하려는 순간). **베이크오프(비교) 여부와
무관하게 항상 거친다** — 단일 아이콘 하나만 요청받은 경우도 포함(위 description 참고,
2026-09-13 개정). 라운드8의 도장처럼 "이거 하나만"으로 시작한 단일 요청이 실제로는
후보까지 만들며 재작업된 사례가 있어, 비교 생략 여부와 이 단계는 별개로 둔다.

**산출물(강제)** — 그리기 전에 한 줄:

> 🃏 **기성 자산:** {아이콘셋} — 필요한 {N}종 중 {M}종 존재 / 없음({근거})

기본 후보 = **Phosphor 듀오톤**(1512종, MIT). [[preferences]]의 "납작한 라인아트 탈락,
옅은 면+진한 선 채택" 취향과 **같은 기법**으로 만들어져 있다(`fill="currentColor"` +
뒷면 path `opacity="0.2"`). 같은 아이콘을 6가지 굵기로 제공하므로 **라인↔듀오톤 전환이
파일 교체 한 번** — 라운드7식 "I1 라인 vs I3 듀오톤" 베이크오프 자체가 불필요해진다.
라인아트만 필요하면 Lucide(1837종, ISC).

- 개별 조달: `https://raw.githubusercontent.com/phosphor-icons/core/main/assets/duotone/<name>-duotone.svg`
- 목록 확인: git trees API(`/repos/phosphor-icons/core/git/trees/main?recursive=1`)로
  전체 이름을 받아 필요한 아이콘명을 grep — 기억으로 "있을 것"이라 단정하지 말 것.

**직접 그리는 것은 기성셋에 없을 때만.** 실측으로 확인된 예외 2종(2026-09-13):
- **한글 맥락 자산**(예: "가"에 밑줄/취소선) — 기성은 라틴 글자 기준이라 대체 불가.
- **아이콘 일부만 다른 색**(강조색 포인트) — 듀오톤은 두 path가 같은 `currentColor`를
  공유하므로, opacity path에 `fill`을 주입하는 로더 한 단계가 필요하다(샘플 5/5에서
  첫 path가 opacity path로 일관돼 규칙적 주입이 가능).

**왜** — PDF Studio에서 손으로 그린 17종이 **전부 기성셋에 이미 있었다**(2026-09-13
GitHub 실조회: Lucide 17/17, Phosphor 듀오톤 15/15). 라운드8은 도장 후보 3개를 만들고
참고 이미지까지 받아 재설계했지만 `stamp` 한 파일로 존재했고, 라운드12는 아이콘 하나를
두 라운드 만에 만들었다 지웠다. 자산을 손으로 만드는 한 이 시행착오는 매 프로젝트
반복된다 — 아이콘 SVG는 Qt(`QSvgRenderer`)·웹 양쪽에 그대로 들어가는 **스택 무관 공용
자산**이라 한 번 조달하면 계속 쓴다.

### 1단계 — 스코프 좁히기
대상이 넓으면(예: "전체 UI 개선") `deep-interview`로 이번 라운드가 다루는 범위(화면 대상 하나로
좁히기)·고정 제약(예: 라이트테마는 이번에 제외)·완료 기준(시안 확정까지 vs 코드 반영까지)을
먼저 정한다. 대상이 이미 좁으면(예: "이 버튼 색만 바꿔서 5개 더") 생략하고 바로 2단계.

**대상이 "구조/뼈대"급(레이아웃 골격·내비게이션 패턴처럼 정답이 여러 개가 아니라 애초에 뭘
만들지 자체가 불확실한 경우)이면, 후보를 생성하기 전에 레퍼런스부터 모은다.** 사용자에게
레퍼런스를 달라고 하지 말고 스킬이 직접 찾는다 — 대상 도메인의 상용 제품 2~3개를
`WebSearch`/`WebFetch`로 찾아 화면 구조를 캡처하거나 설명으로 정리해 후보 생성의 근거로
쓴다. 이유: 근거 없이 맨땅에서 구조 후보를 생성하면 "다 좋아 보여서" 고른 것이 실사용 후
뒤집히기 쉽다(실사례: PDF Studio 프로젝트 — 근거 없이 낸 구조안이 실사용 피드백으로 3라운드
연속 반전됨, 아래 "뼈대 재검토" 절 참고). 대상이 이미 좁은 축(색·모양 등)이면 이 단계는
생략 — 그건 그라운딩이 아니라 바로 비교로 가는 게 맞다.

### 2단계 — 후보 구성 정하기
몇 개를 누구에게 맡길지 정한다. 기본 추천: Claude 라이브 CSS 2~3안 + 게이트웨이 모델당 2안.
`preflight.py image`로 잔액·비용을 사용자에게 보여준 뒤 진행(저렴해서 승인 대기는 불필요,
비용·모델 추천 근거는 항상 한 줄로 고지 — kairos 스킬 규칙 그대로).

**트리거(관찰 가능)** — 후보를 만들기 시작하기 직전.

**산출물(강제)** — 후보를 하나라도 만들기 *전에* 이 한 줄을 답에 남긴다:

> **전달 경로:** 라이브 하네스(격리 포트 N) / Artifact — {근거 한 토막}

**「라이브 하네스」는 대상이 「이미 실행 중인 앱의 화면」일 때다**(5-B단계). 판정에 실데이터·
실폭·실동작이 필요하면 이미지도 Artifact도 그걸 못 준다. 반대로 아이콘·로고처럼 **앱 밖에서
판정 가능한 자산**이거나, 사용자가 다른 PC·나중에 볼 상황이면 Artifact가 이긴다(링크·평가
위젯·원격). 둘 다 아니면 Artifact가 기본값이다.

⚠ **이 줄을 건너뛰면 기본값이 관성으로 정해진다** — 실사례(2026-09-19 CIMON 상세패널): 대상이
400px 사이드패널이라 **실폭이 판정의 전부**였는데, 이 판단을 안 하면 그냥 Artifact에 확대
목업을 올렸을 것이고 5-A단계의 「실제 렌더 크기」 함정을 그대로 밟는다.

### 3단계 — 게이트웨이 이미지 생성

⚠ **먼저 「이 라운드에 이미지가 필요한가」를 판정한다 — 필요 없으면 통째로 건너뛴다.**
기준은 하나: **판정이 실데이터·실폭·실동작에 달려 있으면 이미지는 원리적으로 못 준다.**
정보 위계·배치·상태 표시처럼 「실제 화면에서 어떻게 읽히나」가 축이면 빼고 라이브로 간다
(2단계의 전달 경로가 「라이브 하네스」면 대개 여기도 생략이다).
CIMON에서 두 라운드 연속 실측된 근거다 — 팔레트 라운드는 "실제 레이아웃을 정확히 반영해야
하는 비교라 라이브 CSS가 어차피 더 적합"해서 스킵했고, 입체감 라운드는 생성해 봤더니
"무드보드가 실물과 너무 달라 참고 가치 없음"으로 판정됐다(`projects/cimon.md`).
**이미지가 이기는 자리는 「아직 아무것도 없을 때의 분위기 탐색」**이다 — 만들 것이 이미
화면에 있으면 그 화면을 고쳐 보여주는 쪽이 항상 정확하다.

- 같은 프롬프트 템플릿을 콘셉트별로 **강조색/스타일 키워드만 바꿔** 재사용한다 — 나머지 문장이
  같아야 "이 축만 비교"가 공정해진다(오늘 세션 D1~D5: 머티리얼 구조 프롬프트 고정, 색 문장 한 줄만 교체).
- 상태가 있는 UI(호버·눌림 등)는 "N가지 상태를 한 장에 그려라"라고 명시해 하나의 이미지에
  담는다 — 정지 이미지가 인터랙션을 못 보여주는 한계를 보완하는 유일한 방법.
- 생성 직후 Read 도구로 이미지를 직접 열어 확인한다(자체검증, 전역 규칙 11-d) — 라벨이 깨졌거나
  요청과 다르게 나온 안은 이 단계에서 걸러낸다.

### 4단계 — Claude 라이브 시안 작성
실제로 동작하는 HTML/CSS로 같은 수의 콘셉트를 만든다. 게이트웨이 이미지와 달리 진짜
`:hover`/`:active`/`:disabled` 상태를 구현해 사용자가 직접 마우스로 체감하게 한다 — 이게
이미지 시안 대비 이 축의 유일한 강점이므로 반드시 살아있는 CSS로 만든다(스크린샷 아님).

### 5단계 — 조립·전달 (2단계에서 고른 경로로)

**5-A = Artifact**(기본값, 아래) / **5-B = 라이브 하네스**(그 아래). 둘을 섞지 않는다 —
같은 라운드를 두 곳에 올리면 사용자가 어디서 판정할지 헷갈리고 취합도 갈린다.

#### 5-A단계 — Artifact로 조립
- 이미지가 있으면 그대로 base64 embed하지 말고 **PIL로 리사이즈(폭 ~800px)+JPEG 압축(quality
  ~80)** 후 embed한다 — 원본 그대로 넣으면 안 하나당 1MB급이라 여러 장이면 수 MB짜리 페이지가
  된다. 파이썬 스크립트로 "템플릿 HTML의 플레이스홀더를 data URI로 치환"하는 빌드 단계를 따로
  두면, 이후 라운드에서 이미지만 추가/교체하기 쉽다.
- **후보는 「실제 렌더 크기」를 반드시 같이 올린다(2026-09-13 신설).** 확대 목업만 보여주면
  사용자가 크게 보고 고른 뒤 실제 화면에서 다시 지적하는 왕복이 생긴다 — PDF Studio에서
  라운드7·8·9·11·12로 **다섯 번** 반복됐고, 기록 본문도 이미 "목업에서 멀쩡하던 아이콘도
  실제 툴바 크기(20px)에서 다시 확인해야 한다"고 지목하고 있다. 각 후보 카드에 확대본과
  **실제 크기 스트립**(실제 px·실제 테마 배경색 위·인접 요소까지 포함)을 나란히 놓고,
  "판정은 아래 실제 크기를 보고 해 달라"고 카드에 명시한다. 실제 px 값은 코드에서
  확인한 값을 쓴다(짐작 금지).
- 각 후보에 `A1`/`B1`처럼 짧은 ID를 붙이고, 페이지 상단에 "요소별로 섞어 골라도 된다"고
  명시한다 — 통짜로 하나만 고르게 하면 여러 모델을 부른 의미(다양성)가 줄어든다.
- **후보 카드마다 평가 위젯을 기본으로 붙인다(2026-09-05, 이전엔 6단계의 선택사항 →
  기본으로 승격).** `artifact-capabilities` 스킬을 먼저 로드해 이 계정에 `db` capability가
  있는지 확인 — 있으면 각 후보의 시각 요소 바로 아래에 좋음/싫음/애매 버튼 + 의견
  textarea + 상태 표시줄(`.rate` 블록)을 붙이고 `capabilities: {db: {}}`로 게시한다.
  버튼 클릭 시 `db.doc('ratings/' + 후보id).set({rating, comment, ts})`로 즉시 저장하고,
  페이지 로드 시 `.get()`으로 기존 값을 복원해 새로고침해도 유지되게 한다. `db`가 없으면
  위젯 자리에 "표시만 됨 — 채팅으로 알려주면 됨"으로 폴백한다.
  **위젯은 페이지 하단에 별도로 모으지 말고, 그 후보를 보여주는 카드 안에 바로 붙인다**
  — 비교 대상과 판정이 한 화면에 붙어 있어야 후보별로 정확히 취합된다. (실사례:
  Eng Shorts 프로젝트에서 하단 바 시안 4종+챕터 행 시안 4종, 총 8개 후보 각각에 위젯을
  붙이자 정상 작동. 처음엔 "콘셉트별 집계 카드 4개"를 페이지 맨 아래 별도 섹션으로
  묶었다가, 후보(카드)와 판정이 분리돼 있어 "그 콘셉트가 좋다"는 게 정확히 어느 화면
  조합을 가리키는지 애매해져 사용자가 재작업을 요청했다 — 후보 단위 = 카드 단위여야
  한다는 원칙을 이걸로 확정.)
- 발행 후 가능하면 `mcp__claude-in-chrome`으로 직접 렌더 확인한다. 브라우저 확장이 연결 안 되어
  있으면 "자체확인 불가"라고 명시하고 사용자 확인에 맡긴다(전역 규칙 11-d, 억지로 우회하지 않는다).
  ⚠ **claude.ai 아티팩트 뷰어는 cross-origin iframe이라 이 브라우저 자동화로 스크롤·`find`가
  안 먹는 경우가 있다** — 레이아웃만 볼 땐 게시한 로컬 HTML 사본을 `python -m http.server`로
  띄워 확인(단 `window.claude.*`는 정적 파일엔 없음), `db` 같은 capability 동작 자체를
  확인해야 하면 뷰포트 최상단(스크롤 불필요)에 위젯 하나만 담은 별도 probe 아티팩트를
  띄워 클릭→`read_db`로 왕복 확인 후 정리한다(상세: 전역 메모리
  `claude_in_chrome_artifact_iframe_limits`).

#### 5-B단계 — 라이브 하네스 (실행 중인 앱의 화면일 때, 2026-09-19 신설)

**앱 사본에 후보 CSS/JS + 전환 바를 주입해 격리 포트에 띄우고, 사용자가 같은 자리에서
후보를 즉시 전환하며 판정한다.** 후보를 나란히 놓는 것보다 **같은 자리에서 깜빡 전환**하는
편이 차이가 잘 드러난다(2026-09-04 입체감 라운드에서 토글로 확인된 방법).

**⚠ 원본을 고치지 않는다.** 사본에만 주입하고, 서버가 그 사본을 가리키게 한다. 채택된 뒤에야
원본에 반영한다(7단계의 「시안 확정과 코드 반영 분리」가 여기서도 그대로다).

⭐ **후보는 가능한 한 CSS만으로 만든다 — 이게 이 경로의 속도다.** 렌더 함수를 건드리지
않으면 후보 3개가 몇 분이고, 원본과 갈릴 일도 없다. 배치는 `order`/`flex`, 숨김은
`display:none`, 크기·색은 그대로 CSS다. 실측(CIMON 상세패널): 3라운드 9후보 중 JS가 필요했던
것은 「정상 상태 판정」 하나뿐이었다.
- CSS로 안 되는 후보만 JS를 쓰되 ⚠ **판정 로직을 복제하지 말 것** — 원본이 이미 붙여 둔
  클래스(`.lv-*` 등)를 **읽어서** 쓴다. 복제하면 후보와 원본이 조용히 갈려, 후보에서 고른
  동작이 반영 후에 달라진다.

**하네스 코드는 그 프로젝트가 소유한다.** 주입 지점·렌더 함수명·이벤트 리스너가 앱마다 달라
범용 템플릿은 대부분 안 맞는다. 스킬이 갖는 것은 절차와 아래 함정뿐이다.
(참고 구현: `AROS_Reverse_Eng_260803`의 `tools/build_bakeoff.py` — 후보 정의를 비운 채
커밋돼 있어 라운드마다 채워 쓰고, 채택 후 다시 비운다.)

**격리(⚠ 필수)** — 포트뿐 아니라 **그 앱이 쓰는 상태 파일 전부**를 따로 준다. 운영과 공유하는
설정·워크스페이스가 하나라도 남으면 테스트가 실사용을 오염시킨다(CIMON 실측: 포트를 갈라도
`dashboard_workspace.json`은 그 PC의 모든 서버 프로세스가 공유했다).

**함정(실측으로 밟은 것)**
- ⚠ **전환 바 클릭에 `stopPropagation`이 필수다.** document 레벨 바깥클릭 리스너가 이 바를
  「바깥」으로 보고 열려 있던 패널·팝업을 닫아버린다 — 후보를 바꾸는 순간 판정 대상이 사라진다.
- ⚠ **후보 CSS는 `</style>` 바로 앞에 넣는다.** 특정도가 같으면 뒤에 선언된 규칙이 이기므로,
  앞에 넣으면 기존 규칙에 밀려 **조용히 안 먹는다**(에러도 안 난다).
- ⚠ **선택자 스코프를 넓히지 말 것.** 같은 그릇(컨테이너)을 여러 모드가 공유하는 경우가 많다 —
  단일 대상 모드에만 있는 요소를 앵커로 잡는다. 실측: 상세패널 규칙이 알람 보기에도 걸려
  메타가 이력 표 아래로 내려갔다. **후보를 올리기 전에 그 그릇을 쓰는 다른 모드를 전부 열어 본다.**
- ⚠ **지난 라운드의 `localStorage` 값이 남는다.** 지금 라운드에 없는 후보 id면 기준점으로
  되돌릴 것 — 안 그러면 사용자가 옛 후보를 보고 있는데 그 사실을 모른다.
- ⚠ **패널을 다시 그리면 JS로 붙인 장식이 날아간다.** 값 갱신·대상 전환 때 원본이 innerHTML을
  통째로 다시 쓰므로, 렌더 함수를 감싸 다시 붙인다.

**자체확인(전역 규칙 11-d)** — 사용자에게 넘기기 전에 **후보를 전부 직접 렌더해 본다.** 헤드리스
브라우저로 각 후보 전환 + 스크린샷 + 콘솔 에러 0을 확인하고, **판정이 갈리는 경우**(정상/이상,
값 있음/없음, 종류가 다른 대상)를 골라 각각 확인한다. 이 경로는 실앱이라 이게 싸다 — 안 하면
사용자가 후보를 누를 때마다 깨진 것을 대신 발견하게 된다.

### 6단계 — 좁혀가기 라운드
사용자가 채팅으로 "모양은 A1, 색은 B4"처럼 직접 말하거나, 5-A의 위젯에 쌓인 좋음/싫음/애매+의견을
`Artifact` 도구의 `read_db`(`collection: "ratings"`)로 읽어와 확인한다(5-B는 사용자가 같은 PC에
앉아 있는 경로라 채팅 한 줄이 가장 빠르다 — 평가 위젯을 따로 만들지 않는다). 어느 경로든
**마음에 든 후보 하나를 고정**하고 그 후보의 프롬프트에서 **딱 한 축만** 바꿔 추가
배리에이션을 만든다(색만 5개 더, 형태만 3개 더 등). 여러 축을 한 번에 흔들면 뭐가
좋았는지 다시 헷갈린다.

⭐ **한 라운드가 끝나면 그 자리에서 원본에 반영하고 다음 라운드를 올린다**(5-B, 2026-09-19 실측).
라운드를 쌓아 두면 후보가 「이전 라운드 채택분 + 이번 축」이 아니라 「기준점 + 이번 축」이 되어
판정이 실제 화면과 어긋난다. 반영 → 회귀 확인 → 다음 축이 한 사이클이고, 이렇게 해서 한 세션에
3라운드(배치 → 제목 위계 → 상태 표시)를 돌았다.

### 7단계 — 수렴
최종 확정되면 hex 색상·모양(둥근 정도·그림자 유무)·상태별 스타일을 하나의 스펙으로 정리한다.
- 취향 문서가 있으면 이번 라운드의 확정 내용 + 탈락한 콘셉트와 이유를 그 자리에서 바로 追記한다
  (미루면 "왜 탈락시켰는지"가 휘발된다).
- 이 스펙을 실제 코드에 반영하는 건 별도 단계로 넘긴다 — 시안 확정과 코드 반영을 한 라운드에
  섞으면 승인 전에 코드부터 손대는 사고가 난다(전역 규칙 12 승인 게이트).

## 성공 기준
사용자가 후보 중 하나 이상을 구체적으로 지목("이 모양+이 색")하며 확정 의사를 밝힌다. "다 괜찮아
보이는데?" 같은 애매한 반응이면 아직 안 끝난 것 — 요소별로 다시 좁혀야 한다.

## 뼈대(구조) 재검토 — 확정된 것을 다시 열 때

**트리거** — 이미 취향 문서에 확정으로 기록된 구조적 결정(레이아웃 골격·내비게이션 패턴 등,
색·모양 같은 말단 축이 아니라 여러 화면에 걸치는 결정)에 대해 실사용 후 "이게 최선이냐"는
재검토 요청이 들어오는 순간.

**절차**
1. 재검토 후보를 만들기 전에 `~/.claude/design-system/projects/<slug>.md`에서 **이전 확정값과
   그때 근거를 먼저 인용**한다 — 뭘 왜 그렇게 정했는지 모른 채 다시 비교하면 같은 이유로 또
   같은 결론(또는 근거 없이 반대 결론)에 도달하기 쉽다.
2. 2~7단계(후보 구성→생성→비교→수렴)를 그대로 진행한다.
3. 결과를 아래 셋 중 하나로 분류해 기록한다(팀3 하네스 C단계 라우팅 차용):
   - **국소 결함** — 표면 속성 하나만 문제(예: 간격만 불균일). 그 속성만 고치고 구조는 유지.
     재검토를 "이전 확정 유지"로 짧게 기록.
   - **방향 오류** — 구조 자체를 바꾼다. 취향 문서에 "라운드N — 이전값→새값, 이유"로 기록.
   - **반복 실패** — **같은 요소가 이 프로젝트에서 3번째로 뒤집히는 경우.** 그 요소를 또
     재조정하기 전에, 그 축이 아니라 **애초 요구사항(PRD) 해석 자체가 틀렸을 가능성**을
     사용자에게 명시적으로 물어야 한다("이 부분을 계속 바꾸는 대신 원래 요구사항부터 다시
     맞춰볼까요?"). 취향 문서에 같은 요소명으로 3번째 항목을 적기 **전에** 이 질문을 반드시
     던진다 — 질문 없이 3번째 반전을 그냥 기록하지 않는다.

**왜 3회인가** — PDF Studio 프로젝트에서 레일 동작·주석도구 위치가 라운드1→3→4→5를 거치며
근거 대조 없이 반복 반전된 실제 사례가 있었다(각 라운드가 이전 확정을 왜 뒤집는지 대조하지
않고 새로 비교만 반복함). 정확한 상한이 3이라는 근거는 아직 없음(추정) — 데이터가 쌓이면
조정.

## 함정
- **같은 구조적 결정을 이전 근거 대조 없이 반복 재검토하면 라운드마다 뒤집힌다.** 나쁜 예:
  "레일이 이거면 좋겠다"는 재검토가 들어올 때마다 매번 새 후보만 만들어 비교하고 이전 확정
  이유는 안 봄 → 대신: 위 "뼈대 재검토" 절차 1번(이전값·근거 먼저 인용)을 거른 채 진행하지
  않는다.
- **확대 목업만 보고 확정하면 실제 크기에서 뒤집힌다.** 나쁜 예: 크게 그린 목업에서 고른
  듀오톤 아이콘이 20px 툴바에서 앞장·뒷장이 뭉개져 사각형 하나로 보여 다음 라운드를 또 돎
  → 대신: 5-A단계의 "실제 크기 스트립"을 반드시 같이 올리고 판정 기준을 그쪽으로 명시한다.
  (대상이 실행 중인 앱의 화면이면 애초에 5-B가 이 함정을 원리적으로 없앤다 — 실폭 그대로다.)
- **기성 아이콘셋을 확인하지 않고 SVG부터 그리기 시작한다.** 나쁜 예: 도장 아이콘 후보
  3개를 직접 그려 비교했는데 `stamp`가 기성셋에 이미 있었음 → 대신: 0-c단계의 한 줄을
  먼저 쓴다.
- **전달 경로를 안 고르면 Artifact가 관성으로 정해진다.** 나쁜 예: 실행 중인 앱의 400px
  사이드패널을 고치는데 확대 목업을 Artifact에 올려, 사용자가 크게 보고 고른 뒤 실제
  화면에서 다시 지적 → 대신: 2단계의 「전달 경로」 한 줄을 후보 생성 *전에* 쓴다.
- **라이브 하네스에서 후보를 JS로 만들며 판정 로직을 복제한다.** 나쁜 예: 「정상이면 초록」을
  후보 쪽에서 새로 계산 → 원본의 판정과 미묘하게 갈려 반영 후 동작이 달라짐 → 대신: 원본이
  이미 붙여 둔 클래스를 읽는다(5-B).
- **정지 이미지에 인터랙션 상태를 요구하지 않으면 호버/눌림을 아예 비교할 수 없다.** 나쁜 예:
  "버튼 디자인 시안 만들어줘"라고만 시켜서 "평상시" 모습 한 장만 받고, 사용자가 "호버하면 어떻게
  생겼어?"라고 되묻게 만듦 → 대신: 프롬프트에 "NORMAL/HOVER/PRESSED/DISABLED 4행"을 처음부터 명시.
- **원본 해상도 이미지를 그대로 base64 embed하면 Artifact가 무겁다.** 나쁜 예: 1.5MB짜리 PNG
  4장을 그대로 넣어 6MB짜리 페이지를 만듦 → 대신: 리사이즈+JPEG 압축 스크립트를 먼저 거친다.
- **같은 프롬프트를 재호출해도 모델은 이전 결과를 기억하지 못한다.** 색상 배리에이션을 만들 때
  "이전과 똑같이, 색만 바꿔서"라고 짧게 쓰면 모양까지 미묘하게 달라진다 → 대신: 원래 프롬프트
  전문을 그대로 복사하고 색 지정 문장 한 줄만 바꿔 재사용한다.
- **게이트웨이 호출이 가끔 Cloudflare 524로 실패한다.** 스턱루프가 아니라 일시적 타임아웃이니
  같은 프롬프트로 1회 재시도하면 대개 성공한다 — 접근을 바꿀 필요 없음.
- **여러 축(모양+색+질감)을 동시에 바꾼 후보끼리 비교하면 사용자가 "뭐가 좋았는지" 특정할 수
  없다.** 6단계에서 반드시 한 축만 고정 변경한다.
