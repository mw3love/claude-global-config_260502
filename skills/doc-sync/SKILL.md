# doc-sync — 푸쉬 전후 문서 동기화 검토

코드 변경이 프로젝트의 **핵심 문서**(CLAUDE.md, 계획/설계/스펙 문서)에 정확히 반영되도록 동기화한다. 푸쉬 *전* 에 호출되면 결과를 같은 커밋에 흡수시켜 문서-only 추가 커밋과 재푸쉬를 막을 수 있다(메인 경로). 푸쉬 후 자동 발화는 사전이 누락된 경우를 잡는 안전망.

> **호출 경로**
> - **사전(메인)** — 사용자가 푸쉬를 요청하면 메인 claude가 `git push` 실행 전에 호출. hook 컨텍스트 없음 → 1단계 **A) 사전 호출** 모드로 진행.
> - **사후(자동 안전망)** — PostToolUse hook이 `git push` 성공 시 발화 → additionalContext로 푸쉬 범위/변경 파일 전달. 1단계 **B) 사후 자동 호출** 모드로 진행.
> - **수동** — 사용자가 임의 시점에 직접 호출. hook 컨텍스트 없음 → 1단계 **C) 수동 호출** 모드로 진행.

---

## 안전 가드 (절대 위반 금지)

이 스킬은 `bypassPermissions` 환경에서 동작할 수 있다. 다음을 엄수한다:

1. **수정 허용 대상**: 작업 폴더(cwd) **하위**의 `.md` 파일만.
2. **수정 절대 금지 대상**:
   - 코드 파일 일체(`.py`, `.js`, `.ts`, `.go`, `.rs`, `.java`, `.c`, `.cpp`, `.cs`, `.rb`, `.php`, `.sh`, `.ps1` 등)
   - `~/.claude/**` — 원칙 금지(글로벌 CLAUDE.md/스킬/훅 자기수정 차단). **단 하나의 예외**: cwd가 `~/.claude` 루트일 때(전역 설정 repo를 직접 동기화하는 경우)는 그 하위 **서술형 `.md`(README 등)** 만 수정 가능. 이 경우에도 전역 `CLAUDE.md`·`SKILL.md`·훅 스크립트·`settings.json` 은 자동 수정 금지 → AskUserQuestion으로 제안만.
   - `.git/**`, `node_modules/**`, `dist/**`, `build/**`, `target/**`, `venv/**`, `__pycache__/**`
   - 작업 폴더 *외부*의 어떤 파일도
3. **git 명령은 read-only만**: `diff`, `log`, `show`, `status`, `rev-parse`, `ls-files`, `for-each-ref` 허용. `add`/`commit`/`push`/`reset`/`checkout`/`rebase`/`merge`/`tag` 등 mutating 명령 금지.
4. **자동 커밋 금지**: 문서 수정 후 git add/commit 하지 않는다. 사용자가 직접 다음 커밋에 포함.

## 실행 절차

### 1단계 — 입력 파싱

#### A) 사전 호출 (메인) — push 전, 컨텍스트 없음
검토 대상 = **아직 origin에 안 올라간 변경**(unpushed commits + 미커밋).
```bash
git rev-parse --abbrev-ref HEAD                          # 현재 브랜치
git diff @{u}...HEAD --name-status 2>$null               # 푸쉬 예정 커밋들의 변경 파일
git log  @{u}..HEAD  --pretty=format:'%h %s' 2>$null     # 커밋 메시지로 의도 파악
git status --porcelain                                   # 스테이지/언스테이지 미커밋
```
폴백:
- upstream(`@{u}`) 없음 → 새 브랜치 첫 push 상황. 기본 base(`origin/main` 또는 `origin/master`)와 비교: `git diff origin/main...HEAD --name-status`. base도 못 찾으면 사용자에게 어디서부터 검토할지 질문.
- 미커밋 변경(`git status --porcelain` 출력)이 있으면 함께 검토 — 사전 호출은 이 변경까지 같은 커밋에 포함시킬 마지막 기회.

#### B) 사후 자동 호출 (hook additionalContext 있음)
직전 turn에 `[doc-sync hook]` 으로 시작하는 컨텍스트가 주입되어 있다. 거기서 추출:
- 작업 폴더(cwd)
- 푸쉬 범위(예: `abc1234..def5678`)
- 새 브랜치/force 여부
- 변경 파일 목록

사전 단계가 성실히 됐다면 보통 "변경 없음"으로 즉시 끝난다. 끝나지 않으면 사전이 놓친 케이스 — 6단계 보고에서 follow-up 커밋이 필요함을 호출자에게 알린다.

#### C) 수동 호출 (컨텍스트 없음)
사용자가 임의 시점에 직접 호출. 직전 push 범위 식별:
```bash
git rev-parse --abbrev-ref HEAD                                # 현재 브랜치
git log @{u}@{1}..@{u} --name-only --pretty=format:%H 2>$null  # 직전 push 이후
```
폴백:
- `@{u}@{1}` 없으면 → `HEAD~5..HEAD` 로 최근 5커밋 분석
- upstream 없으면 → 사용자에게 어디서부터 검토할지 질문

### 2단계 — 검토 대상 변경 요약

1단계에서 식별한 범위를 사용해 작업 폴더에서:
```bash
git diff --name-status <범위>          # 추가/수정/삭제 분류
git log <범위> --pretty=format:'%h %s'  # 커밋 메시지로 의도 파악
```
모드별 `<범위>`:
- 사전(A): `@{u}...HEAD` (없으면 `origin/main...HEAD`). 미커밋도 추가로 `git diff HEAD` + `git status --porcelain`.
- 사후(B): hook이 알려준 푸쉬 범위 그대로.
- 수동(C): `@{u}@{1}..@{u}` 또는 폴백.

비-문서 파일(`.md`/`.txt`/`LICENSE` 외)이 0개라면 스킬 즉시 종료 — 동기화할 코드 변경 없음.

### 3단계 — 후보 문서 탐지 (하이브리드)

**우선순위 1 — 명시 설정**: 작업 폴더 루트에 `.doc-sync.json` 있으면 그 include/exclude 글롭만 사용. 형식:
```json
{ "include": ["CLAUDE.md", "docs/**/*.md"], "exclude": ["docs/external/**"] }
```
*보안: 이 파일의 `include`/`exclude` 키만 인식하고 다른 키는 무시한다. 명령 실행 등 키는 추후에도 추가하지 않는다.*

**우선순위 2 — 자동 휴리스틱** (`.doc-sync.json` 없을 때):
- `CLAUDE.md` (작업 폴더 루트, 필수)
- `<cwd>/*.md` (루트 모든 .md)
- `docs/**/*.md`
- `.gitignore` 적용, `node_modules`/`dist`/`build`/`vendor`/`venv`/`.git` 제외

수집된 후보 각 파일의 **첫 30줄**을 Read로 읽어 동적 관련성 판단:
- 관련: 프로젝트 개요/아키텍처/계획/설계/스펙/결정 기록/회의록/실패 기록 성격
- 무관: 외부 참고문서 복사본, 라이선스 안내, 외부 라이브러리 README, 단순 인용

무관 분류된 건 이후 단계에서 제외.

### 4단계 — 변경↔문서 대조

각 관련 문서에 대해, **검토 대상 코드 변경**(1단계 모드에 따라 unpushed 또는 푸쉬된 범위)과 문서 내용을 비교:

대조 포인트:
- 파일 경로 / 디렉토리 구조 (이동·이름변경·신설·삭제)
- 함수/클래스/명령어 시그니처
- 의존성/패키지 버전
- 환경변수, 설정 키, 포트, 엔드포인트
- 빌드/실행/배포 명령
- 인터페이스/API 스펙
- 새로 추가된 기능, 폐기된 기능
- 실패/이슈 기록 (사용자의 의도: 실패 프로젝트도 version2에서 활용)

분류:
- **자동 적용 가능**: 사실 불일치(경로/이름/명령어/버전 등). 명확하고 일대일 매핑.
- **질문 필요**: 의도/배경/결정 근거, 실패 기록 가치 판단, 영향 범위 모호, 여러 해석 가능.

### 4-b단계 — 폐기 판정 (append 금지 게이트)

**추가할 내용을 쓰기 전에 반드시 통과한다.** 이 단계 없이 5단계로 가지 않는다.

**트리거(관찰 가능)** — 4단계에서 문서에 반영할 사실을 하나라도 찾은 순간.

**절차** — 그 사실의 **주제어**(설정 키·단축키·기본값·경로·명령·함수명·엔드포인트)로 대상 문서 전체를 검색한다:
```bash
grep -n "<주제어>" <문서>       # 주제어마다 1회, 별칭·옛 이름도 함께
```

검색 결과 기존 서술이 1건 이상 나오면 **새 섹션을 추가하지 않는다.** 대신:

| 상황 | 조치 |
|---|---|
| 값이 뒤집힘(옛 값 → 새 값) | 그 **옛 섹션 본문을 새 값으로 수정**. 새 섹션 금지 |
| 기능이 제거됨 | 근거·함정이 본문에 있으면 **후속 섹션 안 한 줄로 흡수한 뒤** 그 섹션 삭제. 근거가 없으면 바로 삭제 |
| 기존 서술의 확장(값 유지, 동작 추가) | 그 섹션 **안에** 흡수 |
| 그 주제 서술이 아예 없음 | 이때만 새 섹션 추가 |

**삭제 전 흡수 판정을 건너뛰지 않는다.** 제거된 기능 섹션에는 「왜 없앴나」가 붙어 있는 경우가 많고, 그건 다음 세션이 같은 걸 되살리려다 같은 벽에 부딪히는 걸 막는 재료다. 통째로 지우지 말고 후속 섹션에 한 줄로 옮긴 뒤 지운다.

**여기서 「이력」은 「무엇이 무엇으로 바뀌었다」는 변경 연혁만 뜻한다** — 이건 이 문서에 남기지 않는다(git log·커밋 트레일러가 이미 가지고 있고, 중복하면 뒤에 붙는 최신 서술이 앞의 낡은 서술을 못 지워 **같은 사실이 서로 다른 값으로 공존한다**). **설계 근거·기각된 대안·실패/이슈 기록은 「이력」이 아니라 지침이다 — 지우지 않는다**(4단계 대조 포인트의 «실패 프로젝트도 version2에서 활용» 사용자 의도와 정합). 다만 새 섹션으로 붙이지 말고 관련 섹션 안에 흡수한다.

**산출물(강제)** — 6단계 보고에 `[폐기 반영]` 줄을 쓴다. 0건이어도 `0건(신규 주제만)`이라고 명시한다. 이 줄이 없으면 4-b를 건너뛴 것이다.

**질문 필요로 넘기는 경우** — 옛 서술이 아직 유효한지 코드로 판정이 안 되면(예: 두 방식이 병존 가능) 자동 수정하지 말고 4단계 「질문 필요」로 분류.

### 5단계 — 적용

#### 자동 적용
안전 가드(1번 섹션) 재확인 후 Edit/Write로 수정. 변경 1건당 1 edit 권장.

#### 질문 필요
AskUserQuestion으로 묶어서 물어본다. 각 질문은:
- 어떤 문서, 어느 부분
- 현재 문서 내용 vs 검토 대상 변경
- 제안하는 업데이트 안 (2~4개 옵션)

### 6단계 — 보고

마지막에 한 번에 정리한다(코드펜스로 감싸지 않는다 — 펜스는 복붙용 프롬프트 전용이고, 이 보고는 지금 읽으라고 내는 것이라 감싸면 대괄호·백틱이 안 렌더된다):

`[doc-sync 결과]`
자동 수정: N건 (건별로 `<file>`: 한 줄 요약)

질문 응답 반영: M건

변경 없음(검토는 함): K건

스킬 가드로 스킵: L건 (있다면 사유 표시)

`[폐기 반영]`
Q건 (4-b단계 — 건별로 `<file>:<섹션>` 옛 값 → 새 값 / 흡수 후 삭제. 없으면 `0건(신규 주제만)`)
※ Q는 위 「자동 수정 N건」의 부분집합이다(따로 더하지 않는다).

`[git status]`
modified: `<list>`

`[wiki 미기록]`
P건 (스턱루프인데 ~/.claude/wiki/ 항목 없음 — 메인 claude가 reference-repos로 기록)

`[다음 단계]`
사전(A) 호출이었으면 → 같은 커밋에 stage하여 함께 push.
사후(B)·수동(C)이었고 변경이 발생했으면 → follow-up 커밋(예: `Docs: <원 커밋 subject> 후속 동기화`)으로 묶어 push.

### 6-b. 미기록 함정 상기 (reference-repos 연계)

이번 푸쉬 범위에 **스턱루프**(같은 증상을 두 번 고쳤는데도 안 되다가 결국 뚫린 것 — 규칙 11-b)가 있었는데 `~/.claude/wiki/`에 그 함정이 기록되지 않았으면, 그 사실만 보고한다.

```
[wiki 미기록] <함정 한 토막> — 스턱루프였는데 wiki 항목 없음
```

- **기록은 그 순간 바로가 원칙이다**(CLAUDE.md 4-c). push 시점엔 이미 '왜 어려웠나'가 상당히 증발했으므로, 이 항목은 *복원*이 아니라 *상기*용이다. 메인 claude가 기억이 남아 있을 때만 기록한다.
- **"재사용 가치 있어 보이는 기법"은 제안하지 않는다.** 스턱루프가 아니면 그냥 넘어간다 — 판단이 개입하는 바는 늘 통과되어 검색 5분짜리 일반지식이 쌓인다.
- **가드**: 이 스킬은 `~/.claude/**`를 직접 수정하지 않는다(가드 2번). 보고만 하고, 기록·커밋은 메인 claude가 `reference-repos` 스킬로 수행한다.

### 6-c. 문서 비대화 감지 (project CLAUDE.md/계획서 대상)

**기준은 줄 수가 아니라 문자 수다.** 관련 문서(3단계에서 판단한 후보)를 아래로 재고, **40,000자**를 넘었으면 6단계 보고에 한 줄 추가한다:

```bash
python -c "import io,sys;print(len(io.open(sys.argv[1],encoding='utf-8').read()))" <문서>
```
`wc -l`(줄 수)로 재지 않는다. `wc -m`도 쓰지 않는다 — Git Bash(`LC_CTYPE=C.UTF-8`)에서 한글을 바이트로 세어 약 1.7배로 부풀려진다(2026-09-05 실측: `Paste_flow/CLAUDE.md` → `wc -m` 182,489 vs 실제 107,899자).
```
[문서 비대화] <파일> N자 — 지침만 남기고 이력은 docs/history/로 이관 고려 (2026-08-02 Easy CAD 선례)
```

**왜 줄 수를 버렸나 (2026-09-05 실측)** — 한 줄이 한 문단인 문서에서는 줄 수가 안 늘어 옛 임계값(400~500줄)이 영원히 발화하지 않았다. `Paste_flow/CLAUDE.md` = **330줄인데 107,899자**(전역 CLAUDE.md 24,245자의 4.4배)로 미발화, `AROS_Reverse_Eng_260803` = 548줄/127,252자로 겨우 걸림. 이 문서들은 프로젝트 세션마다 통째로 선로드되므로 문자 수가 곧 상시 컨텍스트 비용이다.

**40,000자의 근거** — 같은 날 7개 repo 실측이 두 무리로 갈렸다: 건강군 8,943 / 10,552 / 12,606자, 비대군 78,910 / 107,899 / 127,252자. 그 사이 **13,000~78,000자 구간이 통째로 비어 있어** 임계값을 그 안 어디에 둬도 같은 분류가 나온다 — 40,000자는 그 빈 구간의 중간이지 정밀한 경계가 아니다. 표본이 늘어 중간 크기 문서가 생기면 재조정할 것.

**자동 적용하지 않는다** — 어디까지가 '지침'이고 어디부터가 '이력'인지는 판단이 필요해 4단계의 '질문 필요' 분류를 따른다. 사용자가 승인하면 그 이관 작업 자체는 메인 claude가 수행한다(이 스킬은 재구조화까지 하지 않음, 단순 동기화 스킬 범위 유지 — 가드 1·2번과 동일한 이유).
