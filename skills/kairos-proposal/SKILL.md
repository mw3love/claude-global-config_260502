## 실행 절차

### 1단계 — 프로젝트 문서 스캔

대상 경로에서 다음을 우선순위대로 Read/Glob한다: `README.md`, `CLAUDE.md`, `PRD/*.md`, `task-list.md`, 그 외 루트의 `*.md`. 문서가 부실해 특정 항목(특히 제안 의도·기대효과)을 채울 근거가 없으면 지어내지 말고 사용자에게 짧게 물어본다.

### 2단계 — 항목별 내용 확정

- **제안명/한줄소개/제안 의도/주요 기능/구현 현황/비고**: 문서 내용을 근거로 작성(재작성·요약 가능, 문서에 없는 사실을 만들어내지 않는다). **비고에 개인 전역관리용 도구·개인 인프라(예: 여러 PC 동기화 스크립트 등 본인만 쓰는 사적 자동화)는 언급하지 않는다** — 신청 대상 서비스와 무관한 개인 셋업 노출(2026-08-24 사용자 피드백: sync-repos 언급 삭제 요청)
- **기대효과**: 문서에 정량 수치(절감 시간·처리 건수 등)가 없으면 숫자를 지어내지 말되, `[확인 필요]`류 꼬리표를 달지 말고 정성적 효과를 자연스러운 문장으로 서술한다(신청서는 사용자가 직접 채워 제출할 완성본이지 검토용 초안이 아니다 — 2026-08-24 사용자 피드백: "적당한 말로 작성해줘")
- **활용 대상 및 확산 범위**: 문서 내용(특정 부서 전용 도구인지, 범용 도구인지)을 근거로 셋 중 하나를 추천하고, **AskUserQuestion으로 사용자에게 확인받은 뒤** 최종 반영한다(스킬이 임의로 확정하지 않는다)

### 2-b단계 — 문서 스타일 (2026-08-24 사용자 피드백)

- **구분자는 슬래시(`/`)** — 나열(A와 B, A·B, A, B)을 표현할 때 가운데점(`·`)이나 쉼표(`,`)를 단어·항목 사이 구분자로 쓰지 말고 `/`를 쓴다. 단, 원본 템플릿이 이미 갖고 있는 문장부호(문장 안 자연스러운 쉼표, 원본의 `·` 불릿 마커, `AAA, BBB` 형태의 코드/파일 나열은 아님)까지 바꾸지는 않는다 — "여러 항목을 나열하는 구분자"만 대상.
- **불릿 기호를 적극 사용** — 마크다운 문법(`#`, `**` 등)은 HWP에 그대로 찍히므로 쓸 수 없지만, 목록성 내용(주요 기능, 비고 등)은 각 줄 앞에 `- `를 붙여 문단 구분을 시각적으로 분명히 한다. 원본 템플릿에 이미 `·` 불릿이 있는 필드(구현 현황 및 방안)는 그 스타일을 그대로 유지한다.
- 줄간격은 `set_cell`이 원본 셀의 첫 문단 서식을 그대로 복제하므로 필드마다 크게 달라지지 않는다 — 이상해 보이면 `safe_window_shot.py`로 실제 렌더링을 먼저 확인하고 판단한다(추측으로 서식을 건드리지 않는다).

### 3단계 — HWP 작성

1. 원본 템플릿을 바탕화면에 `KAIROS_제안서_{서비스명}.hwp`로 복사(서비스명은 프로젝트 대표 명칭 — README 제목 등에서 추출). 원본은 절대 직접 수정하지 않는다.
2. `hwp-from-data`의 `hwp_edit.py`(`HwpDoc`)로 복사본을 열어 위 셀 매핑대로 `set_cell(row, col, [lines], append=False)`.
3. `doc.replace(...)`로 접수 월 채우기.
4. `doc.save(path)`.

### 3-b단계 — 페이지 분리 대응 (내용이 많아 표가 제목과 분리되거나 표 자체가 쪼개질 때)

콘텐츠가 많은 서비스(예: KBS Monitoring v2)는 제목만 1페이지, 표가 2~3페이지로 밀려날 수 있다(2026-08-24 실제 발생). 원인 순서대로 확인·조치한다:
1. `hwp.KeyIndicator()[3]`로 `MoveDown`을 반복하며 실제 페이지가 바뀌는 지점을 찾는다(표가 쪼개지는지, 제목과 분리만 되는지 구분).
2. **셀 문단의 줄간격이 과도하게 넓으면**(원본 안내문구가 1줄만 예상하고 150~160%로 잡아둔 경우) `hwp_edit.py`의 `_tight_parashape_id`가 채우는 시점에 자동으로 130%로 낮춘다 — 이미 엔진에 반영되어 있어 최신 버전이면 별도 조치 불필요.
3. 그래도 제목과 표가 분리되면 **페이지 여백(`PAGEMARGIN`)을 단계적으로 줄인다**: 원본 Top/Bottom(약 1.5cm, HWPUNIT 4252)을 1cm(2835) → 0.5cm(1417) 순으로 낮추며 매 단계 재검증한다. `_ln(e.tag)=="PAGEMARGIN"`인 요소의 `Top`/`Bottom` 속성을 직접 수정하면 된다(전체 문서에 적용되는 단일 속성이라 셀 단위 조치보다 간단).
4. 내용을 줄여서 맞추지 않는다 — 사용자가 명시한 사실 내용을 지면 확보를 이유로 빼면 안 된다. 여백·줄간격 조정으로도 안 맞으면 페이지 수가 늘어난 채로 두고 사용자에게 보고한다.

### 4단계 — 검증 (필수, `hwp-from-data` 규칙 그대로)

저장본을 다시 열어 ① 채운 셀 값이 남아 있는지, ② `hwp.PageCount`가 비정상적으로 폭증(20+)하지 않았는지 확인한다. 통과 못 하면 "완료"라고 보고하지 않는다. 표·서식이 시각적으로 멀쩡한지는 `hwp-from-data/safe_window_shot.py`로 자체 확인한다(전역 규칙 11-d) — **전체화면 캡처는 절대 쓰지 않는다**(포커스 실패 시 사용자의 다른 무관한 창이 찍히는 사고 위험, 2026-08-24 실제 발생). 창을 못 찾으면 시각 확인은 생략하고 사용자에게 직접 열어 봐 달라고 안내한다.

## 범위

- 최종 산출물은 `.hwp` 완성본 하나다. 검토용으로 같은 내용의 MD를 바탕화면에 같이 남겨도 되지만(원문/도출/작성 구분이 쉬움), 필수는 아니다 — 사용자가 원치 않으면 생략 가능.
- 한 프로젝트 경로에서 여러 신청서를 뽑는 경우는 다루지 않는다(1경로 = 1신청서 고정 전제).
