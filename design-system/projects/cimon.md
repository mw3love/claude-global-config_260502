## 확정 (2026-09-04, 팔레트 1라운드 — 중립색 색조)

**문제 제기**: "어두운 영역에도 코랄끼가 있다" — `--bg`/`--panel`/`--border`가 강조색(`--accent`,
코랄 `#e08361`)과 같은 따뜻한 색상군으로 틴트돼 있었음. 코드 조사 결과 `--accent`가 57곳에
쓰여 배경 전반의 "흔한 코랄" 인상에 기여.

**진행**: Claude 라이브 CSS로 실제 컴포넌트(상단 사이트탭·좌측 서브탭·구분선·위젯카드·알람행)
조각을 그대로 재현해 후보 비교(게이트웨이 이미지는 이 라운드에선 스킵 — 감시운용PC에
`JBNU_GATEWAY_API_KEY` 미설정, 실제 레이아웃을 정확히 반영해야 하는 비교라 라이브 CSS가
어차피 더 적합했음). 강조색은 전 라운드 고정, 중립색만 변경(한 축 원칙).

**1라운드 (색상군 자체)** — 그래파이트(완전 무채색) / 슬레이트(차가운 청회색) / 차분한 세피아
(원래 계열 채도만 낮춤) 3안 + 기준점. **슬레이트 채택** — "코랄색이 더 돋보여서 좋다"
(보색 대비 효과를 사용자가 스스로 짚음).

**2라운드 (냉색 강도)** — 슬레이트 방향 안에서 옅게(B1)/1라운드 값 그대로(B2)/짙은 네이비(B3)
3단계 비교. **B1(옅게) 채택** — "깔끔하고 좋다". 1라운드의 "돋보임"보다 절제된 인상이 최종
기준이 됨 — 대비 강도는 약한 쪽을 선호(`preferences.md`의 "화려함보다 절제" 항목과 일치,
2번째 프로젝트 확인으로 그 항목을 가설에서 확인됨으로 승격시킨 근거이기도 함).

**최종 검증**: 확정 후보 위에 기존 의미색(경고 주황 `--warn`, 위험 로즈 `--danger`, 이상탐지
마젠타 `--anomaly`)을 함께 배치해 서로 구분되는지 확인 — 그대로 확정.

## 입체감 elevation 라운드 (2026-09-04 착수, 2026-09-11 판정 완료 — 아래 "확정" 참조)

`preferences.md`의 Material 스타일 선호 가설(Easy CAD 단일 출처)이 이 프로젝트에서도 성립하는지
판정받는 라운드. 카드 수십 개가 동시에 깔리는 감시용 대시보드 특성상 강한 그림자가 노이즈가 될
수 있다는 우려도 같이 판정 대상. **결론: 가설 기각** — Material 강한 입체감은 이 프로젝트에는
안 맞음(C1 평면 유지). Easy CAD 하나에서만 성립하는 취향으로 남음, 프로젝트마다 다시 확인할 것.

**후보 구성**: Claude 라이브 CSS 3안(실제 마우스 hover 가능) + gpt-image-2 무드보드 2안.
- C1 평면(지금 방식, 기준점) — 테두리 1px만, 그림자 없음.
- C2 은은한 입체 — 패널을 한 단(`#22262d`) 밝히고 옅은 그림자, 호버 시 2px 상승.
- C3 강한 입체(Material) — 패널을 두 단(`#282d35`) 밝히고 테두리 제거, 진한 다층 그림자,
  호버 시 4px 상승+확대.
- G1/G2 — gpt-image-2로 "은은한/강한 입체감" 무드보드 각 1장(참고용).

**다크 배경에서의 함정(실측)**: 배경(`#14161a`)이 이미 거의 검정이라 그림자만으로는 층이 거의 안
보인다 — Material Dark 스펙대로 **패널 표면 자체를 단계적으로 밝히는 것**을 그림자와 병행해야
실제로 읽힌다. C2/C3의 패널색 차이가 그래서 있다.

**게이트웨이 이미지의 한계(정직하게 페이지에 명시함)**: gpt-image-2가 "은은한"/"강한" 그림자
강도를 문장 지시만큼 정밀하게 구분해 그리지 못했다(G1/G2 육안으로 유사) — 이 축의 정밀 판정은
라이브 CSS(C1~C3)로 하고, 게이트웨이 이미지는 분위기 참고로만 쓰라고 페이지에 직접 밝혀 뒀다.

**대량 배치 테스트**: 카드 10개 그리드를 C1↔C2↔C3 버튼으로 전환하며 "잡음이 되는지"를 그 자리
에서 확인할 수 있게 만듦(별도 정적 스크린샷 3장이 아니라 토글 인터랙션 하나로).

**Artifact**: `https://claude.ai/code/artifact/924c39fc-fbf1-4584-b6ce-3151e2046420`
(favicon 🎚️, "위젯 카드 입체감").

## 확정 (2026-09-11, 판정 완료)

**결론: C1(평면) 채택 — 단, 호버 상호작용만 수정.** C2/C3의 상시 그림자·표면 밝힘은
전부 기각(대량 배치 섹션에서도 같은 판단 유지 — "1번과 의견 같음"). gpt-image-2
무드보드(G1/G2)는 실물과 너무 달라 참고 가치 없음으로 판정.

**변경 지점 — 호버**: 지금 C1의 호버(`border-color: var(--accent-dim)`)를 버리고,
**테두리 색은 그대로 두고 `translateY(-2px)`로 살짝 뜨는 것만** 넣는다. 그림자는
추가하지 않음(사용자가 명시한 것은 "2px 뜨는 것" 하나뿐이고, 이번 라운드 전체가
"그림자는 노이즈가 될 수 있다"는 우려에서 출발했으므로 안 물어본 그림자를
임의로 얹지 않음).

**변경 지점 — 선택 상태**: "위젯을 선택하면 테두리 코랄"을 요청함 — 확인해보니
기존 다중선택 모드(`.widget.ws-selected`, L369)가 이미 `border-color: var(--accent);
box-shadow: 0 0 0 1px var(--accent)`로 정확히 이 처리를 하고 있음. 사용자 의도가
①이 기존 걸 그대로 유지하라는 뜻인지, ②"대화하며 설명할 때 클릭 한 번으로
가볍게 강조"하는 새 상호작용(체크박스 등 다중선택 UI 없이)을 원하는 것인지
**확인 필요** — 코드 반영 전 질문함.

⚠ 아직 `tools/dashboard.html`에 호버 변경 미반영(선택 상태 스코프 확인 후 함께 반영 예정).

⚠ **작업 중 실측한 함정 2건(재사용 가치, 여기 기록)**:
- `text-wrap: balance`가 아니라 **IBM Plex Mono에 한글 글리프가 없어서** 폴백 시 음절 사이
  간격이 들쭉날쭉해지는 버그였다("위젯"이 "위 젯"으로 벌어짐) — 처음엔 balance를 의심했으나
  무관했다. 한글 섞인 헤딩엔 모노스페이스 폰트 스택을 쓰지 말 것(순수 라틴/숫자 라벨에만).
- Artifact 안 CSS 셀렉터 특정도 동률 함정 — 뒤에 선언된 규칙이 이긴다는 걸 잊고 `.mcard`
  변형 클래스를 앞서 선언했다가 스타일이 안 먹은 적 있음(이번엔 순서를 맞춰 회피).

## 상세패널 3라운드 (2026-09-19, 판정·반영 완료)

아날로그 상세패널의 위계·강조·배치를 한 세션에 3라운드로 좁혔다. **게이트웨이 이미지와
Artifact를 둘 다 뺀 첫 라운드** — 대신 `tools/build_bakeoff.py`(격리 포트 + 후보 전환 바)로
실데이터·실폭·실동작 그대로 비교했다. 이미지를 뺀 근거는 이 문서의 앞 두 라운드 실측
(팔레트 = "라이브 CSS가 어차피 더 적합", 입체감 = "무드보드는 실물과 너무 달라 참고 가치 없음")
이고, 이번 과제는 정보 위계·배치라 **실폭 400px이 판정의 전부**여서 더 맞지 않았다.

| 라운드 | 축 | 채택 | 기각 |
|---|---|---|---|
| 1 | 남는 세로 265px를 누구에게 | **A** Info를 맨 아래로 | B 차트 최대 · C 값 최대 |
| 2 | 구역 제목의 위계 | **E** 제목 최소화(`지금`·`INFO` 삭제) | D 주-부 2단 · F 액센트 마커 |
| 3 | 정상/이상을 무엇으로 | **H** 숫자 앞 상태 점 | G 정상도 색 · I 구역 띠 |

**드러난 취향 — 「키우기」보다 「덜어내기」.** 세 라운드 모두 사용자는 요소를 **키우거나
더하는 안**(B·C·D·F·G·I)을 전부 버리고 **덜어내거나 조용한 안**(A·E·H)을 골랐다. 2라운드에서
제목을 키우는 D 대신 **지우는** E를 고른 것이 가장 선명하다. `preferences.md`의 "화려함보다
절제"와 같은 방향이고, 이 프로젝트에서 **세 번째** 확인이다(팔레트 2라운드의 "옅게" 채택,
입체감 라운드의 평면 유지에 이어).

**함께 나온 규칙 — 색은 숫자에 쓰지 않는다.** 3라운드에서 26px 헤드라인 숫자의 레벨색을
걷어내고 점으로 옮겼다. 근거: 이 패널에서 가장 자주 읽는 것이 숫자 자체라 **가독성을 상태
신호와 맞바꾸면 안 된다**(특히 `--ok` 초록은 흰색보다 대비가 낮다). 상태는 옆에 따로 쓴다.

**절차에서 배운 것** — 0-b 원칙 자가진단이 **비교 없이 5건**을 걷어냈고(중복 문구·어절 중간
줄바꿈·라벨 역전·팔레트 잔재), 그만큼 라운드에서 다툴 것이 줄었다. ⚠ 다만 자가진단으로 올린
6건 중 1건은 **사용자가 이미 그 자리로 정한 것**이어서 뺐다 — 「객관적 결함」으로 보이는 것도
프로젝트 문서(`docs/dashboard.md`)에 결정 기록이 있는지 먼저 볼 것.

## 디지털 상세패널 4라운드 (2026-09-19, 판정·반영 완료 — 하네스 라운드 7~10)

아날로그 3라운드와 같은 라이브 하네스(`tools/build_bakeoff.py`, 격리 8792)로 디지털 쪽을 좁혔다.

| 라운드 | 축 | 채택 | 기각 |
|---|---|---|---|
| 7 | 차트 ON/OFF 색 | **D** 초록 면 + 회색 선 + 축 `● 현재 상태` | A 선도 ON 초록 · B 축 ● 없음 · C 면 없이 선만 |
| 8 | 순간 반전 목록 | **D** 펼침 표(최근 5건+요약) + 차트 주황 점선 | A 표만 · B 20건 전부 · C 차트만 |
| 9 | 누적 ON 표현 | **B** %만 + 비율 막대 | A 시간+% 유지 + 막대 |
| 10 | 「상태 유지」 위치 | **A** 헤드라인 아래 한 줄 | B 헤드라인 옆(날짜 툴팁) |

**드러난 취향 — 「덜어내기」 네 번째 확인 + 「색은 한 곳에」.** 7라운드에서 ON을 선·면 둘 다
초록으로 칠한 A 대신 **면만** 초록인 쪽을 골랐고, 9라운드에서도 글자를 줄인 B를 골랐다.
단 **「덜어내기」가 「정보를 숨기기」는 아니다** — 10라운드에서 날짜를 툴팁으로 숨긴 B를 버렸고,
7라운드 B를 보고 사용자가 직접 "위젯처럼 `● ON` 표기는 왜 없나"라고 되물었다(위젯과 **같은
말을 하는 것**이 덜어내기보다 우선). 요약하면: 같은 정보를 두 번 말하지 말되, 화면에서 사라지게 하지도 말 것.

### 하네스에서 밟은 함정 (`tools/build_bakeoff.py`에도 기록)

- ⚠ **`table-layout:fixed` + 인라인 `<colgroup>` 표의 칸 폭은 `td`가 아니라 `<col>`이 쥔다.**
  `td{width}`는 조용히 무시되고, `td{display:none}`은 남은 칸이 **한 칸씩 앞으로 밀린다**.
- ⚠ **`box-sizing:border-box`에서 「작은 width + 패딩」으로 히트 영역을 만들면 오히려 줄어든다**
  (실측 30 → 20px). 총 크기를 직접 주고 `margin`으로 발자국을 맞출 것.
- ⚠ **행 높이를 바꾸는 후보는 페이지 스크롤을 같이 재라.** 행 수가 `floor(가용높이/행높이)`라
  **1px 변화가 한 행을 더 넣고** 그게 스크롤로 드러난다(17라운드에서 실제로 발생).
