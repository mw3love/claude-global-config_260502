기능 추가/안전망/추상화/대안 설계 같은 비-단순 변경을 제안할 때는 **토론 단계에서 코드 수정을 멈추고**, 의견 비교 → 트레이드오프 정리 → 사용자 명시 선택을 거친 뒤에 실행한다. 단순한 단일 변경(설정값 1개 수정 등)으로 99% 해결된다면 거기서 멈추는 게 우선이고, 추가 안전망은 "새 실패 모드를 만들 위험"을 명시적으로 비교한 뒤 결정한다.

**Why:** 2026-05-18 정파 오진입 검토 중 사용자가 "내 의견과 너의 의견을 같이 비교하고 어떤게 좋은지 계속 논의하자. 실제 코드 수정 진행은 하지마"라고 명시. 또 빠른 해제 안전망 제안에 대해 "코드가 지저분해진다던지 그로인해 불필요한 오류가 생기지 않을까 하는 의심"을 표명. 결국 단일 설정 변경(`still_trigger_sec` 60→120)만 채택하고 안전망은 보류함.

**How to apply:**
- 옵션 제시 시 **표 형태로 5/18 같은 실제 사례 기준 장단점 비교** (확률, 새 실패 모드, 코드 라인 증가, CLAUDE.md 원칙 부합 여부)
- "점진적 접근" 옵션을 항상 후보에 포함: 단순 변경 먼저 → 데이터 누적 후 필요 시 추가 검토
- 사용자가 "ㄱㄱ" / "진행" 명시 전까지는 Edit/Write 보류. 단 사용자가 결정 사항을 명확히 답한 직후의 실행 작업은 진행 가능.
- "is_in_signoff_window=True" 같은 코드 식별자 기반 설명보다는 "지금 시각이 정파 시작~끝 사이" 같은 **운영 시나리오 기반 설명** 선호
