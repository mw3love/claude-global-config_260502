`web_prototype/`(리포 하위, PyQt 본체 `easycad/`와 별개)는 더 이상 "웹 전환 여부를 판단하는
실험"이 아니라 **병행 개발 트랙**이다 — 사용자가 명시: "병행해서 둘 다 끝까지 만들어보고 싶은게
지금 마음. 다만 웹 쪽이 구현이 늦게 시작했으니까 균형을 맞추기 위해 웹에 집중해서 개발하려는
것"(2026-08-05). 즉 Python(PyQt) 앱과 웹 버전을 **둘 다 완성**시키는 게 목표이고, "당분간 웹에
집중"은 우선순위 결정이 아니라 진도 격차를 좁히기 위한 일시적 배분이다 — "웹이 유망하면 전환,
아니면 폐기" 같은 이분법적 판단 대기 상태가 아니므로, 향후 보고·계획에서 "결론 미정"·"전환 여부
판단" 같은 실험적 프레이밍을 쓰지 않는다.

**시작은 실험이었다(배경 for 왜 SVG+DOM 접근인지)**: "agent 자동검증(playwright)만으로 상호작용
버그를 화면 없이 잡을 수 있는가"라는 가설 검증으로 2026-08-05 착수 — 자동검증만으로 실버그
여러 건 발견+수정, 사용자가 실제 브라우저로 손맛 확인 완료("나쁘지 않다")까지 거쳐 위 병행개발
결정으로 이어졌다. 이 배경은 "왜 웹 쪽만 playwright 자동검증에 크게 의존하는지"를 설명하는
맥락으로는 유효하지만, **지금 시점의 목표 자체를 "실험/검증"으로 서술하면 안 된다.**

**진행 경과(누적)**:
1. 1~2차(포트/커넥터/지속연결) — 자동검증만으로 실버그 1건 발견+수정, 지속연결 1차 구현 통과.
2. 사용자 손맛 확인 완료 → 병행개발 결정(위).
3. 3차(인터랙션 스트레스테스트, AskUserQuestion으로 방향 확정) — 다중선택(고무줄 밴드)+그룹드래그+
   Delete/Escape 구현, 대규모(17도형·22화살표) 자동 스트레스 검증에서 A* 폴백 대각선 버그 1건
   발견+수정. 성능도 같은 라운드에 해결(21.8ms/frame → 연결+근접 화살표만 재계산+드롭 시
   1회 전체 재계산 하이브리드로 2.15ms/frame, 20도형·31화살표 규모 재측정).

**How to apply**: 이 트랙 관련 요청("웹 cad 어디까지 했지" 등)엔 `docs/history/2026-08.md`의
"웹 전환 실험" 항목들(날짜별로 여러 건 누적, 제목은 역사적 명칭이라 "실험"이 남아있음)이 상세
근거, `docs/pitfalls.md` "라우팅(A*/직교 엘보)" 절에 재발 방지용 교훈이 있다. 다음 세션 자연스러운
다음 단계는 아직 미정(무엇을 웹에 추가할지) — 사용자와 방향부터 확인. [[ui-simplicity-principle]]
같은 다른 프로젝트 원칙과는 별개로, 개발 우선순위 판단 시 "웹은 아직 검증 단계라 후순위"라는
과거 프레이밍을 쓰지 말 것 — 지금은 완성 목표가 같은 두 트랙 중 진도가 느린 쪽에 자원을 배분하는
정상적인 프로젝트 관리 상황이다.
