PyQt6에서 사용자가 "이 버튼은 되는데 저 버튼(특히 창 우상단 X)은 안 된다"는 식으로
**조작 경로별로 다른 증상**을 보고하면, `dlg.close()`/`dlg.accept()`/`dlg.reject()`를
스크립트로 호출해 재현하려 하지 말 것 — 이 경로들은 서로 다른 코드를 탄다
(`QDialog.reject()`는 `closeEvent()`를 아예 안 거치고 `hide()`로 직행, X버튼(진짜
WM_CLOSE)만 `closeEvent()`를 거침 — PyQt6 실측으로 확인). 스크립트 `.close()` 호출도
`closeEvent()`를 거치긴 하지만, 진짜 OS 네이티브 창닫기와는 미묘하게 다른 채널이라
**같은 결과를 보장하지 않는다**(2026-08-22 실사례: 스크립트 `.close()`는 안전한데 진짜
마우스로 X를 클릭하면 100% 크래시하는 차이가 실제로 있었음).

**재현 방법(이번에 통한 방법):** PowerShell + `user32.dll` P/Invoke로 실제 창 좌표를
구해 `Cursor.Position`을 옮기고 `mouse_event`로 진짜 클릭을 보낸다. 핵심 함정 2개:
① `SetProcessDPIAware()`를 안 부르면 `GetWindowRect`/`Cursor.Position`이 서로 다른
DPI 가상화 좌표계를 써서 클릭이 엉뚱한 곳에 떨어진다(스크린샷으로 커서가 실제 버튼
위에 있는지 클릭 전에 항상 눈으로 확인할 것). ② 멀티모니터 환경에서 창이 보조 모니터
(음수 좌표)에 뜨면 좌표를 primary 기준으로 착각하기 쉬움 — `GetWindowRect`가 돌려준
좌표를 그대로 믿고 그 창 자신의 rect에서 클릭 좌표를 계산할 것(다른 창/스크린샷 crop
기준으로 하드코딩하지 말 것).

**왜:** "isRunning() 체크 후 e.ignore()" 같은 방어 코드가 있어도, 그 방어가 실제로
작동하는지는 진짜 OS 이벤트로만 검증된다. 이 프로젝트 CLAUDE.md 규칙 11-d("실행 재현도
같은 트리거 — 오프스크린 강제 없이 실제 GUI 프로세스를 직접 띄우고 화면·콘솔 로그까지
확인")가 요구하는 수준이 바로 이것 — API 호출로 대체 가능한 상태확인은 대체해도 되지만,
"버튼을 실제로 눌렀을 때"가 곧 재현조건인 버그는 진짜 클릭이 필요하다.

**연관 실패 사례(같은 세션):** 처음엔 "QThread가 다이얼로그에 parent로 물려있다 파괴되며
크래시"로 오진단하고 `deleteLater()` 자가정리 패턴으로 "고쳤다"고 보고했으나, 그 수정
자체가 **use-after-free**(워커 스레드가 끝나自 `deleteLater()`로 스스로를 지우는데
다이얼로그가 그 파이썬 참조를 계속 들고 있다가 `closeEvent()`에서 재접근)를 새로
만들어 오히려 크래시를 100% 재현 가능하게 만들었다. 원본 코드는 실제 클릭 테스트로
안전함이 확인됐다(수정 없이 되돌리는 게 정답이었음). 교훈: **스크립트 기반 프록시
검증(offscreen, `.close()` 직접호출)만으로 "고쳤다"고 보고하지 말 것** — 실제 클릭
재현 전엔 규칙 11-c의 "프록시검증(실조건 미확인)" 상태로만 보고해야 했다.
