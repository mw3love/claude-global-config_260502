# GUI 상호작용 버그는 스크린샷/동영상 프레임 추측보다 실시간 재현 로그가 훨씬 빠르다

## 함정
EXTEND(Shift+클릭) 버그와 정렬 스냅 버그를 사용자가 보낸 스크린샷 여러 장 + 동영상(mp4)
프레임을 ffmpeg로 잘라 픽셀 좌표를 추측하며 진단했다 — 크롭 오프셋을 몇 번씩 다시 잡고,
정렬 가이드선(마젠타)이 빨간 테두리에 묻혀 안 보이는지 확대해서 확인하고, 커서와 qc-dot의
화면 픽셀 거리를 눈대중으로 재서 임계값과 비교하는 식으로 여러 라운드를 썼다. 그 결과
"커서를 더 정확히 겨냥하라"는 **틀린** 가설을 내놓기까지 했다(실제 원인은 겨냥 문제가
아니라 이벤트가 다른 핸들러로 새는 것이었음). 동영상은 사용자의 실제 클릭/hover/모디파이어
상태를 전혀 담지 못해 원리적으로 한계가 있었다.

## 해법
코드에 임시 파일 로거를 심고, 사용자가 실제로 재현한 뒤 "됐다"고만 알려주면 Claude가
로그 파일을 직접 Read로 읽어 실제 좌표·상태·분기 진입 여부를 확정하는 방식으로 바꾸자
즉시 해결됐다(qc-dot 가로챔, 더블클릭 라벨편집 가로챔, 끝점핸들 가로챔을 각각 로그 한
줄 차이로 확정).

```python
# 모듈 최상단 — 파일 하나, try/except로 항상 안전
_DBG_LOG_PATH = r"C:\Users\<user>\Desktop\<app>\debug.log"

def _dbg(msg: str) -> None:
    try:
        import datetime
        with open(_DBG_LOG_PATH, "a", encoding="utf-8") as f:
            f.write(f"{datetime.datetime.now().strftime('%H:%M:%S.%f')[:-3]} {msg}\n")
    except Exception:
        pass
```

의심되는 각 분기 진입점(press/hover/커밋/더블클릭 등)에 한 줄씩:
```python
_dbg(f"PRESS tool={tool!r} shift={shift} scene=({x:.1f},{y:.1f})")
```

순서: (1) 로거 추가 → (2) 사용자에게 "재현하고 됐다고만 알려달라" 요청 → (3) 로그 파일을
Claude가 직접 Read → (4) 실제 이벤트 순서·좌표·조건 분기를 눈으로 확정 → (5) 고치고 →
(6) **사용자가 명시적으로 "지워도 된다"고 할 때까지 로그는 유지**(한 번 문제가 다
안 풀렸는데 성급히 지웠다가 재요청받은 적 있음 — 진단이 끝났다고 Claude가 판단해도
사용자가 다음 증상을 더 보고할 수 있으므로 임의로 정리하지 않는다).

## 대가
로그 파일이 디스크에 계속 쌓인다(사용자 Desktop 등 프로젝트 밖 경로에 둬서 git 추적
대상이 안 되게 함) — 진단 끝나면 코드에서 `_dbg` 호출부와 헬퍼 자체를 제거해야 영구
부채가 안 됨(제거 타이밍은 사용자 승인 필요, 위 참조).

## 일반화된 교훈
**"말로 설명하기 어려운 상호작용 버그"는 스크린샷 여러 장보다 로그 한 번이 항상 빠르다.**
사용자가 이미 화면을 보고 있으므로 시각 정보는 충분하다 — Claude에게 부족한 건 "그 순간
코드 내부에서 어떤 분기를 탔는가"이고, 이건 스크린샷이 원리적으로 못 담는 정보다. 2회차
이상 스크린샷/동영상 기반 진단이 실패하면(스턱루프 징후), 세 번째 시도 전에 로그 방식으로
전환할 것 — 픽셀 추측을 더 정교히 하는 것보다 훨씬 싸다. 로그 라인은 상태변화 시에만
찍어야(`if prev != new: log(...)`) 무의미한 스팸 없이 정확한 타임라인이 남는다.
