# 스마트 정렬 스냅 — 정점 후보와 bbox 후보의 패딩 불일치

## 함정
`_apply_smart_snap`에 "실제 도형 정점(꼭짓점)" 스냅 후보를 추가하면서, 삼각형처럼
bbox와 실제 외곽선이 다른 도형만 다루면 될 줄 알았다. 그런데 `_RectItem`을 정점
후보에 포함시키자 기존 회귀 테스트(`test_smart_align_center_priority_is_per_shape_
only`)가 깨졌다 — 원인은 **같은 사각형인데 두 값이 0.5유닛 어긋났기 때문**이었다.

- bbox 후보(기존)는 `srect()`가 `_content_rect()`로 계산 — `_RectItem`이 이걸
  override 안 하면 `_HandleResizeMixin` 기본값(Qt `QGraphicsRectItem.boundingRect()`)
  이 쓰이는데, 이건 펜폭/2만큼 자동으로 부풀려진 값이다(펜폭 1.0 → 0.5유닛 패딩).
- 정점 후보(신규)는 `_host_outline_local_polygon()`(TRIM 커널 재사용) — 패딩 없는
  진짜 `rect()` 좌표.

1차 수정은 "회귀만 피하자"며 `_RectItem`을 정점 후보에서 **제외**했다(증상 회피).
그런데 사용자가 실사용(4354% 줌)으로 **같은 병의 다른 얼굴**을 재발견했다 — 사각형
B의 중심을 사각형 A의 변에 "붙였다"고 여겼는데, 화면상 B의 중심점이 A의 실제
테두리 선이 아니라 그 0.5유닛 바깥(패딩된 bbox 값)에 얹혀 "테두리 오른쪽에 있다"고
보였다. 1차 수정은 정점 후보끼리의 충돌만 막았을 뿐, **패딩된 값 자체가 스냅
목표로 쓰이고 있다는 진짜 원인**은 그대로 남겨뒀던 것.

## 해법
`srect()` 쪽을 고쳤다 — `_RectItem`/`_SymbolItem`도 `_host_outline_local_polygon`
(패딩 없는 진짜 외곽선)을 쓰게 바꾸고, 정점 후보는 다시 `_RectItem`을 포함해
vertex×vertex로 직접 교차시켰다. **핵심 교훈: 같은 스냅 후보 풀(pool)에 "패딩된
값"과 "패딩 없는 값"을 섞지 않는다** — 값이 우연히 같은 도형(예: 사각형)에서는
그 둘이 미세하게 어긋나 (a) 동률 판정이 깨지거나(회귀), (b) 눈에 보이는 오프셋
버그(사용자 재현)로 나타난다. 여러 소스에서 bbox/정점을 뽑아 섞을 땐 **모든 소스가
같은 패딩 기준(보통 "패딩 없음")을 쓰도록 통일**하는 게 유일하게 안전한 길이다.

이미 있던 `_LineItem`/`_PolyArrowItem`/`_ArrowItem`/`_EllipseItem`/`_PathItem`용
"실제 기하(패딩 없음)" 우회 코드(같은 파일, 2026-08-10 앞선 커밋)가 정확히 같은
클래스의 문제를 이미 풀어 놨었는데, `_RectItem`/`_SymbolItem`엔 그 우회를 안 걸어
같은 병을 남겨뒀던 것도 뒤늦게 확인됨 — "이 파일에 이미 같은 패턴의 우회가 있다"는
게 발견 즉시 다른 관련 타입에도 감사(audit)해야 하는 신호였다.

## 대가
`_content_rect()` 기반이던 기존 pytest 헬퍼(`_cleft`/`_ctop`/`_cbottom`/`_cright`,
tests/_shared.py)도 같은 패딩 없는 기준으로 다시 정의해야 했다 — 안 그러면 테스트가
"패딩된 예상값"과 "패딩 없는 실제값"을 비교해 새로 깨진다. 관련 테스트 3종의 느슨한
허용오차(`< 1.0`, 패딩 크기를 감안해 일부러 넉넉히 잡아뒀던 것)도 `< 1e-6`으로
조일 수 있었다(그 자체가 "이 오차 관용이 실은 버그를 숨기고 있었다"는 신호였음).

진단에 2번의 라운드가 걸린 이유: 1차 회귀는 오프스크린 pytest로 즉시 잡혔지만,
2차(진짜 원인)는 **고배율 줌에서 실제 `.ecad` 파일을 열어야만** 눈에 띄는 정도의
오프셋(0.5유닛)이라 일반 스모크 테스트로는 절대 못 잡는다 — 사용자의 "여전히 안
됨" 재보고 + 실제 파일 첨부가 결정적이었다(관련: CLAUDE.md 규칙 11-b 스턱루프).
