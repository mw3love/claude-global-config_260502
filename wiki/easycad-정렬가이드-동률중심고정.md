# 정렬 가이드가 "중심만 뜨고 나머지는 안 보임" — 동률 tie-break 자체가 원인이었던 사례

## 함정
스마트 정렬 가이드(도형 이동 중 근처 도형과 모서리·중심 정렬 시 뜨는 마젠타 선)가 "가운데만
뜨고 변(위/아래/좌/우) 정렬은 안 보인다"는 사용자 재현 버그. 규칙 11-b 스턱루프 — 매칭 로직을
3번 패치했는데 안 잡혔다:

1. 1차: 좌-우처럼 역할이 다른 조합(교차 매칭)을 배제(과발화 원인이라 판단해 제거).
2. 2차: 동률(같은 높이 도형은 상/중/하이 동시에 맞음) 시 서브픽셀 흔들림으로 승자가 계속 바뀌는
   플리커를 막으려 "동률이면 항상 중심(center) 채택" 도입.
3. 3차: "마주보는 변" 인접 매칭(A 아랫변=B 윗변) 추가 + 전역 tie-break가 무관한 도형에 도용당하는
   버그 발견·수정(같은 상대 도형 내에서만 tie-break 적용하도록 스코프 축소).

세 번 다 격리 테스트로는 검증됐지만 사용자는 계속 "여전히 가운데만 보인다"고 재현. 여기서
**진짜 마우스 드래그를 내가 직접 재현하려는 시도 자체가 이 앱 창에서 안 통했다**(별도 함정,
아래 «부수 함정» 참조) — 그래서 알고리즘을 더 추측으로 고치는 대신 실제 코드에 임시 진단
로그를 심어 사용자가 재현하게 하고 로그를 직접 분석하는 방식으로 전환했다.

`_apply_smart_snap`에 역할별 최소거리(`_dbg_near`, 문턱 무시)와 최종 `bx`/`by`를 파일에 기록하는
임시 로그(`_ALIGN_DEBUG`)를 넣고, 사용자에게 "python run.py로 방금 상황 재현하고 '다 했다'고만
말해달라"고 요청 → 로그를 직접 읽고 분석.

로그에서 결정적 단서: **두 도형이 완전히 같은 크기(121×73)** 였고, 그 결과 좌/중심/우
(그리고 상/중심/하) 거리가 **모든 프레임에서 소수점까지 정확히 일치**했다(예:
`left=2.5, center=2.5, right=2.5`). 이는 우연이 아니라 수학적 필연이다 — 두 도형의 폭이 같으면
`center = left + width/2`가 양쪽에서 똑같이 오프셋되므로 `center-diff == left-diff == right-diff`가
항상 성립한다(높이가 같으면 상/중/하도 마찬가지). 즉 "동률 시 중심 우선"(2차 패치)은 **같은 크기
도형끼리는 항상, 매번, 예외 없이 적용되는 조건**이었고, 그 결과 변 정렬은 원리적으로 절대
단독으로 뜰 수 없었다. 이 앱은 "열별 박스 폭 통일"을 권장하는 순서도 툴이라 사용자가 같은
크기 도형을 쓰는 게 오히려 정상 사용 패턴이었다 — 즉 버그가 아니라 **직전 수정(2차 패치)의
필연적 부작용**이었다.

## 해법
"동률이면 승자 하나(중심)만 고른다"를 폐기하고, **동률인 역할을 전부 가이드선으로 동시에
표시**하도록 재설계(Figma/Lucid도 여러 정렬이 동시에 맞으면 선을 여러 개 함께 보여준다).
스냅 이동량(dx/dy)은 동률 후보끼리 델타가 항상 같아 어느 걸 써도 결과가 같지만(정의상 동률),
가이드선은 역할마다 그리는 좌표(그 변·중심의 실제 화면 위치)가 서로 다르므로 하나만 고르면
정보가 사라진다. `pick_local()`이 임계 내 후보를 전부 점수 매겨 정렬한 뒤, 최솟값과 근접
동률(`tie_eps`) 범위 안의 후보 전부를 리스트로 반환 → `_align_guides`에 좌표별로(중복 제거)
전부 추가.

## 대가
가이드선이 여러 개(최대 3개) 동시에 뜰 수 있어 시각적으로 더 조밀해진다(같은 크기 도형이
정렬될 때 상/중/하 3줄이 한꺼번에 뜸).

## ⚠ 위 해법은 절반이었다 — 진짜 마지막 원인은 「인접 매칭의 교차축 게이트」
동률 수정 뒤에도 사용자는 "서로 다른 면(A 아랫변=B 윗변)은 붙여야만 뜬다"를 3회 더 재보고했다.
그 사이 내가 시도한 것들(교차축 게이트를 thr만큼 넓히기 → 임계값 6→10px → 가이드선 헤일로)은
전부 빗나갔다. 최종 원인은 인접(마주보는 변) 후보에만 걸어 둔 **"교차축이 겹쳐야 후보로 인정"**
게이트였다:

```python
if nr.left() < orr.right() + thr and orr.left() < nr.right() + thr:   # ← 이 게이트
    y_cands += [(nr.bottom(), orr.top(), "adj"), (nr.top(), orr.bottom(), "adj")]
```

두 도형이 **가로로 나란히 떨어져** 있으면 x범위가 안 겹쳐 이 조건이 거짓 → 아랫변-윗변이 아무리
정확히 맞아도 후보 리스트에 오르지도 못한다. "붙여야만 뜬다"의 정체가 이것이었다(붙어야 교차축이
겹쳐 게이트가 열림). **같은 역할 매칭(좌-좌 등)에는 이런 게이트가 애초에 없다** — 인접에만 건
비대칭이 문제였고, 해법은 게이트를 넓히는 게 아니라 **없애는 것**이었다. 남기는 배제 대상은
「좌-중심」·「중심-우」처럼 기하적으로 의미 없는 4개 조합뿐(원래 과발화의 진범).

**결정적 실패:** 이 답은 **내가 이미 수집한 로그 안에 있었는데 내가 오독했다.** 로그에
`x_gate=False ... adj_top_bottom=4.00 → by=None`(임계 6 이내인데 차단), 심지어
`adj_bottom_top=0.00`(완벽히 일치인데 차단) 줄이 있었는데, 나는 `'adj'`가 **찍힌** 줄만 grep해
"인접 매칭 정상 작동함"이라고 사용자에게 보고했다. **차단당해서 안 찍힌 줄이야말로 증거였다.**

## 교훈 (추가)
- **로그를 볼 때 "발생한 것"만 grep하면 "차단당한 것"을 영원히 못 본다.** 증상이 "X가 안 나온다"면
  X가 나온 줄이 아니라 **X의 전제조건이 거짓인 줄**을 찾아야 한다(`x_gate=False` 같은 게이트 플래그를
  로그에 넣어 둔 것은 옳았는데, 정작 그 플래그로 필터링해 보질 않았다).
- **대칭성 점검이 강력한 버그 탐지기다.** "같은 역할 매칭에는 없는 게이트가 왜 인접에만 있나?"라는
  질문 하나면 3라운드를 아꼈다. 방어 목적으로 조건을 추가할 땐 *형제 코드 경로에도 같은 조건이
  있는지* 확인하고, 없으면 그 비대칭을 정당화할 수 있어야 한다.
- **"완화"는 "제거"의 대용품이 아니다.** 게이트에 `+thr` 여유를 준 완화는 수 px 차이만 구제할 뿐,
  134유닛 떨어진 실제 케이스엔 아무 효과가 없었다. 조건 자체가 틀렸으면 파라미터를 만지지 말 것.

## 부수 함정 — 이 앱 창은 합성 마우스 이벤트로 드래그 재현이 안 됨
직접 재현을 시도하며 두 가지 자동화 경로가 전부 막힘을 확인:
- **합성 QMouseEvent**(`view.mousePressEvent(QMouseEvent(...))` 직접 호출): press는 먹지만
  이어지는 mouseMoveEvent가 Qt의 `mouseGrabberItem`에 델타로 반영되지 않아 아이템이 전혀
  움직이지 않았다(itemChange 훅 기반 핸들 드래그처럼 코드가 직접 상태를 만지는 경로는 이 문제가
  없다 — 순수 Qt 기본 아이템 이동만 막힘).
- **OS 레벨 자동화(pyautogui)**: 실제 마우스 커서는 움직이고 클릭도 발생하지만, 이 창에서는
  선택조차 안 됨(포커스/DPI 스케일링 등 미확정 원인) — 몇 차례 좌표 보정 시도 후 포기.

**교훈**: 이 프로젝트 CLAUDE.md가 이미 "합성 QMouseEvent가 이 창에선 씬으로 배달 안 됨"을
문서화해 뒀는데도(지속연결 초안 관련 기록), 이번에도 새로 시도해서 같은 벽에 부딪혔다 — **이미
문서화된 이 앱 고유의 제약은 재확인하지 말고 바로 신뢰**했어야 시간을 아꼈다.

## 교훈 (일반화 가능한 부분)
- **합성 마우스 이벤트/OS 자동화로 재현이 안 되는 PyQt 앱의 상호작용 버그는, 알고리즘을 더
  추측으로 고치기보다 "임시 진단 로그를 심고 사용자가 실제로 재현하게 한 뒤 그 로그를 직접
  분석"하는 게 빠르다.** 사용자에게 "재현하고 '다 했다'고만 말해달라"는 왕복 최소화 워크플로가
  유효했다(같은 패턴이 `easycad-화살표재부착-자기스냅.md`에도 등장 — 이 프로젝트에서 반복되는
  유효 전략으로 보인다).
- **매칭/동률(tie-break) 로직에서 "특정 역할을 우선"하는 규칙을 넣기 전에, "언제 이 우선순위가
  발동하는가"를 먼저 따져야 한다.** 이번 경우 "동률 시 중심 우선"이 발동하는 조건(두 후보의
  수치가 완전히 같음)이 **두 도형이 같은 크기이기만 하면 항상 성립**하는, 결코 드물지 않은
  케이스였다 — "가끔 발생하는 특수 상황을 안정시키는 미세조정"이라고 생각했던 게 사실은
  "흔한 사용 패턴에서 상시 발동하는 규칙"이었다. 우선순위 규칙을 넣을 땐 그 트리거 조건이 실제
  사용 분포에서 얼마나 자주 참이 되는지부터 가늠한다.
