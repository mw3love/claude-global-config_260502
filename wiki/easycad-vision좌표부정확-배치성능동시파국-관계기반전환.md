# vision 모델 좌표 부정확 → 배치(지저분함)+성능(A* 폭주) 동시 파국 → 관계 기반 배치로 전환

## 함정

이미지→도면 AI 파이프라인(P1 개괄→P2 타일→P3 병합)에서 vision 모델이 추정한 절대 픽셀
좌표(shapes의 x/y/w/h)를 그대로 신뢰해 도형을 배치했다. 사용자가 "지저분해서 못 쓰겠다"고
2번 보고 — 1차 시도(중복박스 IoU+라벨 정규화 이중신호 병합, 타일 경계 넘는 연결선 보완
패스 P3.5 신설)로도 안 풀렸다(스턱루프 트립와이어 발동).

재진단 결과 근본 원인은 **vision 모델의 절대 픽셀 좌표 추정 자체가 부정확**하다는 것 —
같은 실물을 두 번(다른 타일에서) 인식해도 좌표가 몇~수십 px씩 어긋난다(IoU 0.12~0.48로
낮게 나옴, 실측). 이 부정확한 좌표를 그대로 신뢰해 배치하면:

1. **도형이 겹쳐 시각적으로 지저분해진다** — 3차례 dedup 임계값 조정으로도 근본 해결 안 됨
   (좌표 오차 자체가 안 없어지므로 다른 형태로 계속 재발).
2. **그 겹친 도형 더미 사이로 자동 배선(A*)이 지나갈 길을 못 찾아 성능까지 파국적으로
   나빠진다** — 실측: 20개 그룹 드래그 916ms(60fps 예산의 55배). **도형 수는 1600개짜리
   정상 문서보다 훨씬 적은(140개) 이 문서가 44배 더 느렸다** — "도형이 많아서"가 아니라
   "겹쳐 있어서"였다. cProfile로 확인하니 시간의 96%가 A* 자동배선 — 겹친 장애물 사이
   경로를 못 찾아 클리어런스 사다리(설계상 못 찾을 때 더 넓은/좁은 여유로 최대 8~10회
   재시도하는 안전망)를 반복 발동시키고 있었다.

지저분함과 버벅임이 **완전히 무관해 보이는 두 증상이 사실 같은 뿌리(좌표 신뢰 배치)**의
두 얼굴이었다.

## 해법

**좌표를 정밀 배치 근거로 쓰는 것을 완전히 그만두고**, P1~P3.5가 여전히 그대로 뽑아주는
관계 정보(shapes+edges — "무엇이 있고 무엇과 연결되는가")만으로 새로 배치했다:

- 이 앱이 이미 Mermaid 텍스트 가져오기용으로 검증해 쓰던 그래프 레이아웃 엔진
  (`layout_positions()` — 그래프 BFS 레벨 기반, 같은 레벨은 자동으로 안 겹치게 나란히
  배치)을 **그대로 재사용**했다. 새 레이아웃 알고리즘을 새로 만들지 않은 것이 핵심 —
  이미 검증된 "관계만으로 겹침 없이 배치하는" 도구가 이미 있었다.
- 원본의 대략적인 흐름 방향(좌→우 vs 위→아래)은 완전히 버리지 않고 "약하게"만 반영 —
  rough 좌표의 bbox 가로세로 비율로 전체 방향(LR/TD)을 추정하고, 같은 레벨 안 순서도
  rough 좌표로 정렬해 원본과 비슷한 느낌은 유지하되 정밀 위치는 신뢰하지 않았다.
- 셀 크기(배치 격자 한 칸)를 전체 도형 중 최대 크기+여백으로 잡아, 어떤 도형도 자기
  셀을 벗어나지 못하므로 겹침이 **원리적으로 불가능**해졌다.
- 이 배치 교체만으로 그룹 드래그 916ms→675ms(26% 개선, 겹침 관련 재시도가 줄어서).

겹침을 없애도 남은 두 번째 원인(별개)을 재프로파일링으로 발견: A* 클리어런스 사다리가
"경로가 이미 완벽해도" 매번 무조건 추가 탐색을 도는 설계였다 — `fast` 플래그를 호출
체인 전체(reroute→_apply_routing→build_elbow→_route_ortho)에 추가해, "그룹 드래그처럼
한 프레임에 reroute가 몰리는 상황"에서만 조건부로 사다리를 건너뛰게 해 675ms→156ms
추가 개선(총 916ms→156ms, 5.9배).

## 대가

- 원본의 정밀 위치·간격을 포기하는 트레이드오프(사용자가 명시적으로 감수하기로 확정) —
  "사진 같은 그림"이 아니라 "겹침 없는 편집 가능 도면"으로 목표 자체가 바뀜.
- 여전히 60fps 예산의 9배 느림(완전 해결 아님) — 남은 원인(사다리 자체의 구조)은 이 앱에서
  가장 스턱루프가 잦았던 민감 영역이라 더 깊이 들어가지 않고 여기서 멈춤.
- 자체 회귀검증 스크립트를 급히 짜다가 **이미 이 프로젝트에 기록돼 있던 함정**(도형
  경계는 `.boundingRect()`가 아니라 `.rect()`로 재야 함 — 전자는 펜폭 패딩 포함)을
  그대로 재현해, 존재하지 않는 회귀를 실제 회귀로 오판할 뻔했다. 검증 스크립트 자체도
  프로덕션 코드와 같은 정의를 쓰는지 대조해야 한다는 교훈.

## 일반화 가능한 교훈

1. **"부정확한 입력을 사후 보정하는 전략"은 근본 한계가 있다** — 다듬기 전에 "그 부정확한
   값을 아예 안 쓰는 대안이 있는가"부터 검토할 것. vision 모델의 좌표 추정처럼 입력
   정확도에 원리적 한계가 있는 시스템에서는, 출력을 계속 다듬는 접근이 같은 한계 근처에서
   다른 형태로 계속 재발한다.
2. **무관해 보이는 두 증상(시각적 문제 + 성능 문제)이 같은 하나의 부정확한 입력에서
   나올 수 있다** — 각각 따로 고치려 하기 전에 공통 원인을 의심해볼 것.
3. **이미 관계(그래프) 기반 자동배치 도구가 있다면, 좌표 기반 배치가 문제를 일으킬 때
   그걸 재사용하는 게 새 알고리즘을 만드는 것보다 싸고 안전하다.**
